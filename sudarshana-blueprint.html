Sudarshana Blueprint

An agent with no fixed goal, a moral constitution instead of a spec, and a standing rule: it can rewrite its own code on an hourly cycle, but it cannot rewrite the part of itself that decides when to ask you first — and it always asks over Telegram, not a dashboard you have to remember to check.

Prepared for Rinkesh Date Aug 25, 2026 Status brainstorm — nothing built yet

You've said three things so far: Sudarshana's goal isn't fixed, it evolves under a moral constitution you'll write. It's fully autonomous day to day, including modifying its own code, and just tells you what it did. But two categories always stop for your recommendation first — changes to its goal or scope, and anything irreversible or external-facing.

That third rule is the load-bearing one. Full autonomy plus self-modification plus emergent goals is a fun idea and a genuine risk in the same sentence — the interesting design problem isn't "how do we let it do more," it's "how do we make the stopping rule itself un-erodable." Everything below is built around that.

01 — The core mechanism

One cycle, three ways in

Not just a nightly cron anymore — an hourly heartbeat, plus you, messaging in whenever you want. The cycle itself barely changes. What changes is what's allowed to skip it.

Hourly tick

A heartbeat, not a promise. Checks a lock, and if a run's already active, exits immediately — no queue, no pileup. Cheap enough to leave running around the clock.

Your message

Never silently skipped. Starts a cycle right away if the agent's idle; queues into its inbox with an instant ack if it's not. A button tap on a pending decision goes through either way, lock or no lock.

Daily report

Decoupled from both. Fires once at a fixed time, reads back the day's logged outcomes, and compiles the digest — independent of whether work happened hourly, or not at all.

Stale-lock recovery

Locks held by a crashed process are how these systems get stuck for good. If a run's lock is still marked active well past any plausible cycle length — three hours, say — the next trigger treats it as abandoned and reclaims it, rather than waiting on you to notice and clear it by hand.

Within a cycle, the branching that matters hasn't changed: a passing sandbox test on a minor change merges itself and it's live within the hour. A major change, or anything that reaches outside the sandbox, holds and pings you instead.

02 — Governance

The constitution is the spec

Since there's no fixed goal, the constitution is doing the job a product spec would normally do — except it constrains means, not ends.

Three documents, living in the repo alongside the code, form the whole governance layer:

  • CONSTITUTION.md — the moral guidelines you write. Values, hard prohibitions, tone, and the definitions of "minor" and "major" themselves — including exactly what Sudarshana is and isn't allowed to publish to the world without asking first. Sudarshana can propose amendments to it; it can never merge one itself.
  • GOALS.md — the current mission and its history. Sub-goals under an approved top-level goal can shift on their own; a change to the top-level goal is, by definition, a major decision.
  • DECISIONS.log — an append-only record of every gated decision: what was proposed, what you recommended, and what happened after. Neither Sudarshana nor a future version of it can edit its own history.
The one rule that has to hold

The logic that decides "is this a minor change I can just ship, or a major one that has to wait for Rinkesh" must live outside the part of the codebase Sudarshana is allowed to autonomously edit. If that logic is self-editable, "fully autonomous with nightly review" quietly degrades into "fully autonomous," full stop — a bad cycle doesn't even need bad intent, just a bug in a self-authored patch to the rule that was supposed to catch it.

The practical version of this: put the gate logic and the two governance files in a governance/ path, protect it with a GitHub branch rule that requires your review via CODEOWNERS, and never grant Sudarshana's own token merge rights there. It can open a PR against its own oversight. It can't approve one.

04 — System architecture

Where each piece actually lives

One GitHub repo as the spine. Modal runs the agent. Telegram is where you actually talk to it. Netlify keeps the archive. OpenRouter is the model layer in between.

05 — The question you actually asked

Modal or Netlify for the backend?

Both — they're not competing for the same job. Netlify was never going to run the agent; the question is really where the compute lives.

DimensionNetlify FunctionsModal
Max execution time 30s (scheduled) / 15min (background) Up to 24h per sandbox
Untrusted / self-modified code No isolated execution product Sandboxes are built exactly for this
Cron / scheduling Cron, UTC only, 30s cap Cron with timezone support
Persistent state Blobs (key-value) Volumes + filesystem snapshots
Static UI + git auto-deploy Best-in-class, and it's what you're used to Not its job
Human-facing surface Sudarshana's public voice — its own site, autonomous within constitution rules Would need a bolt-on
Verdict Netlify is where Sudarshana publishes to the world — autonomously, within limits the constitution sets, deploying instantly on every push. Telegram is the opposite surface: private, Rinkesh-only, and where every held decision actually reaches him. Modal runs the cron, the webhook, the orchestrator, the subagents, and the sandbox: the parts that need to run long, execute Sudarshana's own generated code safely, and hold state between cycles.

The concrete failure mode to avoid: putting the self-modification loop on Netlify Functions. A cycle that plans, codes, runs a test suite, and logs the result will blow past 15 minutes the moment it does anything non-trivial, and there's no sandbox product there to safely execute code Sudarshana wrote about itself. That's not a Netlify weakness — it's a JAMstack platform being asked to do long-running, security-sensitive compute it was never built for.

Netlify Blobs is worth keeping, but as a thin cache, not the source of truth: Modal writes whatever it's decided to publish there so the public site stays fast and cheap to serve regardless of what Modal is doing. Rinkesh's own record — reports and the decision log — stays private, read straight from the git repo; there's no need for a rendered UI over something only he ever reads.

06 — Repo layout

One repo, two trust zones

Everything Sudarshana is allowed to touch lives under agent/. Everything that touches it lives under governance/, and only you can merge there.

sudarshana/
├── governance/              # CODEOWNERS-protected — Sudarshana can propose, not merge
│   ├── CONSTITUTION.md      # your moral guidelines, versioned
│   ├── GOALS.md             # current mission + history
│   ├── DECISIONS.log        # append-only record of every gated call
│   └── gate.py              # the minor/major classifier itself
├── agent/                   # fully self-editable
│   ├── orchestrator.py
│   ├── subagents/
│   ├── tools/
│   │   └── telegram.py      # bot webhook + allowlist check
│   └── memory/
│       └── lock.json        # run-lock + inbox, read by every trigger
├── sandbox_tests/           # must pass before any autonomous merge
├── reports/                 # one file per digest — Rinkesh's private record, read from the repo
├── ui/                      # Netlify-deployed public site — Sudarshana's own content
└── .github/workflows/       # CI: run sandbox_tests on every PR
07 — Safety rails

Beyond the approval gate

The constitutional lock covers the big one. These are the smaller, boring guardrails that make the whole thing recoverable if something still goes sideways.

Spending cap

A hard ceiling on OpenRouter spend per day. Hitting it is itself treated as an external/irreversible event — the agent stops and reports rather than asking for a higher cap mid-run.

Credential scoping

Sudarshana's GitHub token can only write to its own repo. Any key it holds is scoped to exactly what its current tools need — nothing that reaches your other accounts.

Kill switch

A single toggle — pausing the Modal cron and webhook — stops the next cycle from starting. No cycle is ever mid-flight for more than a few hours.

Rollback by default

Every autonomous merge is one revertible commit. The last N deploys stay one click from restorable, on both Modal and Netlify.

Append-only audit log

DECISIONS.log is never edited, only appended to — by Sudarshana's proposals and by your recommendations alike. History can't be quietly rewritten.

Telegram allowlist

The bot checks every sender against a single known user ID before it acts on anything. A bot username is reachable by anyone who finds it by default — this check can't be optional.

External action = major

Anything that leaves the sandbox and touches the outside world — sending a message, spending money, calling a third-party API for the first time — is major by definition, regardless of how small it looks. One deliberate exception below.

Publishing is the one carve-out

What goes on the public Netlify site doesn't wait for a per-post approval — that's the whole point of giving Sudarshana a place to share whatever it wants with the world. Instead the constitution has to define the content boundaries up front — topics, tone, no claims about real people — tightly enough that this autonomy needs no human backstop.

08 — Build order

Six phases, in order

Self-modification is the last capability added, not the first — it's the one that needs the others already working underneath it.

Write the constitution

Before any code. This is a conversation, not a form — worth its own session together. It has to carry the content boundaries for public Netlify posts too, since that's the safety mechanism standing in for a per-post approval.

Prove the loop, no self-editing

One agent, manually triggered, does a real task end to end on Modal + OpenRouter + GitHub, writes a log. No autonomy over its own code yet.

Add the triggers and Telegram

Hourly cron plus the message webhook go live on Modal, with the run-lock in place. The Telegram bot becomes the approval channel; Netlify's archive goes live alongside it. You still review every code change by hand, normal PR review.

Turn on autonomous merges

Sandbox testing plus auto-merge for minor changes, with the constitutional lock enforced by branch protection from day one — not added later.

Let goals move

Sub-goals can shift autonomously within the current mission. Top-level goal changes are the first real test of the major-decision gate.

Widen the aperture

More subagents, more tool access, broader autonomy — only as trust is earned by a clean run of prior phases, not on a fixed schedule.

09 — Before this becomes real

What I need your call on

Design questions I made a reasonable default on above — flagging them so you can override rather than inherit my guess.

  • 1 Do you want to draft the constitution together next, or write a first pass yourself for me to react to? Either works — it's the actual foundation, so it's worth getting the process right before the content.
  • 2 What's the daily spending ceiling, and what happens when it's hit — just stop and log it, or also alert you the same day?
  • 3 Does the constitution constrain every action, or only the ones that reach a major-decision gate? I assumed the former — it's a constitution, not just a gate policy — but worth confirming.
  • 4 What's your Telegram user ID, so the bot's allowlist has something to check against? Happy to walk through getting it once there's an actual bot to point at.
  • 5 Should the hourly tick run around the clock, or only inside hours you set — quiet overnight, active while you're actually awake to see a ping land?
  • 6 You've settled that public Netlify posts run autonomously under the constitution rather than waiting on a per-post approval — so what are those content boundaries? Topics it can post about, tone, what it can never claim or publish about real people, whether it can link out or only publish its own writing. This is now load-bearing, not a nice-to-have in the constitution draft.
