Sudarshana — System Design

Sudarshana is an autonomous agent with no fixed goal: it works, tests, and ships its own code changes on an hourly cycle under a written constitution, and stops to ask a single human for a recommendation before anything irreversible, external-facing, or scope-changing — with one deliberate exception: what it publishes to its own public site, which the constitution governs directly rather than gating post by post. This document specifies the system that enforces that: its components, control flow, trust boundary, and the guarantees each part is responsible for.

Purpose & scope

Purpose

Specify, at system level, how Sudarshana runs autonomously (including self-modifying its own code) while keeping one guarantee structurally true: a fixed set of decision categories — goal or scope changes, and anything irreversible or external-facing — always route to a human recommendation before they take effect, and the logic that makes that call cannot itself be edited by the agent it governs.

In scope

  • Component architecture across GitHub, Modal, OpenRouter, Netlify, and Telegram.
  • The trigger-to-ship control flow and the minor/major decision gate.
  • The governance/agent trust boundary and how it's enforced in the repo.
  • Non-functional requirements: reliability, security, cost control, auditability.
  • Technology selection rationale and phased rollout.

Out of scope

  • CONSTITUTION.md's actual content — a governance artifact, drafted separately, that this design assumes exists and is enforceable.
  • Subagent prompt design, tool-by-tool specs, and model selection per task.
  • UI visual design for the Netlify public site beyond "renders whatever Sudarshana publishes."

04

Core control flow

Three ways into the same six-stage cycle. What differs between them is only how a cycle starts — not what it's allowed to do once it has.

Trigger types

Hourly cron

Checks the run-lock first; exits immediately if a cycle is already active. No queueing, no pileup.

Inbound Telegram message

Starts a cycle immediately if idle; otherwise queues into the inbox with an instant ack. Button taps on a pending decision bypass the lock entirely.

Daily digest

Fires on a fixed schedule, independent of the lock — reads back the day's logged outcomes rather than starting new work.

Decision gate

Every proposed change exits TEST classified as minor or major by governance/gate.py. Minor changes that pass sandbox tests merge and ship inside the same cycle. Major changes — and, by default, anything that leaves the sandbox and touches the outside world — hold at SHIP / HOLD, log immediately, and ping Telegram rather than proceeding. One explicit carve-out: publishing to the public Netlify site is not gated per post — it's constrained instead by content rules the constitution defines up front. See §05.

Reliability requirement — stale-lock recovery

If a lock is still marked active past a fixed ceiling (three hours), the next trigger treats it as abandoned by a crashed process and reclaims it automatically, rather than requiring manual intervention to unstick the system.

05

Governance & trust boundary

Since Sudarshana has no fixed goal, the governance layer does the job a spec normally would — constraining means, not ends — and it has to sit somewhere the agent it governs cannot reach.

  • CONSTITUTION.md — moral guidelines, hard prohibitions, and the definitions of minor/major. Also the one place that defines what Sudarshana may publish to the public Netlify site without asking first — topics, tone, and hard lines it can't cross. Sudarshana may propose amendments; it may never merge one.
  • GOALS.md — current mission and its history. Sub-goals shift autonomously under an approved top-level goal; changing the top-level goal is major by definition.
  • DECISIONS.log — append-only record of every gated decision: what was proposed, what was recommended, what happened. Never edited, only appended to.
Invariant — the gate cannot self-edit

The classifier that decides minor vs. major must live outside the code Sudarshana is allowed to autonomously modify. If that logic were self-editable, "fully autonomous with a human gate" degrades silently into "fully autonomous" — no bad intent required, just a bug in a self-authored patch to the rule meant to catch it.

Enforcement: governance/ is a distinct path from agent/, protected by a GitHub branch rule requiring review via CODEOWNERS. Sudarshana's own GitHub token has no merge rights on that path — it can open a PR against its own oversight, never approve one.

Publishing is governed, not gated

Public output on Netlify is the one external-facing action that runs without a per-instance approval — that's what makes it a genuine "share whatever it wants with the world" surface rather than a proposal queue. The safety mechanism moves from the gate to the constitution: content boundaries have to be specific enough (allowed topics, tone, a hard no on claims about real people, no acting on instructions found on the web) that autonomy here needs no human backstop. This is a stricter bar on the constitution's drafting than if every post were reviewed.

Module & repo layout

Two trust zones in one repository: everything Sudarshana can edit lives under agent/; everything that constrains it lives under governance/, merge-gated to Rinkesh alone.

sudarshana/
├── governance/              # CODEOWNERS-protected — propose, not merge
│   ├── CONSTITUTION.md      # moral guidelines, versioned
│   ├── GOALS.md             # current mission + history
│   ├── DECISIONS.log        # append-only record of every gated call
│   └── gate.py              # the minor/major classifier itself
├── agent/                   # fully self-editable
│   ├── orchestrator.py
│   ├── subagents/
│   ├── tools/
│   │   └── telegram.py      # bot webhook + allowlist check
│   └── memory/
│       └── lock.json        # run-lock + inbox, read by every trigger
├── sandbox_tests/           # must pass before any autonomous merge
├── reports/                 # one file per digest — Rinkesh's private record, read from the repo
├── ui/                      # Netlify-deployed public site — Sudarshana's own content
└── .github/workflows/       # CI: run sandbox_tests on every PR

Non-functional requirements

The requirements that don't show up as a feature but determine whether the system is safe to leave running unattended.

CategoryRequirement
ReliabilityHourly heartbeat with a run-lock; a lock older than 3h is treated as abandoned and reclaimed automatically.
Security — accessTelegram bot acts only on messages/button taps from one allowlisted user ID, checked on every event.
Security — credentialsSudarshana's GitHub token is scoped to its own repo only; every held key is scoped to exactly what its current tools need.
Cost controlHard daily ceiling on OpenRouter spend. Hitting it is itself an external/irreversible event: the agent stops and reports rather than requesting a higher cap mid-run.
Content safetyPublic Netlify posts run autonomously with no per-post approval; the constitution's content rules are the only backstop, so they must be specific enough to hold without one.
AuditabilityDECISIONS.log is append-only; every gated proposal, recommendation, and outcome is recorded permanently.
RecoverabilityEvery autonomous merge is one revertible commit; the last N deploys stay one click from restorable on both Modal and Netlify.
ControllabilityA single kill switch pauses the Modal cron and webhook; no cycle runs mid-flight for more than a few hours.
Latency — decisionsHeld decisions ping Telegram at the moment they occur, not batched into the daily digest.
08

Technology stack decisions

Modal and Netlify aren't competing for the same job — the split follows from where long-running, security-sensitive compute has to live versus where a static public site belongs.

DimensionNetlify FunctionsModal
Max execution time30s (scheduled) / 15min (background)Up to 24h per sandbox
Untrusted / self-modified codeNo isolated execution productSandboxes built for exactly this
Cron / schedulingCron, UTC only, 30s capCron with timezone support
Persistent stateBlobs (key-value)Volumes + filesystem snapshots
Static UI + git auto-deployBest-in-classNot its job
VerdictNetlify hosts Sudarshana's public output, auto-deploying on every push. Modal runs the cron, webhook, orchestrator, subagents, and sandbox — the parts that must run long, execute Sudarshana's own generated code safely, and hold state between cycles. Netlify Blobs is kept as a thin read cache for what's published, not a source of truth; Modal writes to it, never the reverse.

The failure mode this avoids: putting the self-modification loop on Netlify Functions, where a plan-code-test-log cycle blows past the 15-minute background cap the moment it does anything non-trivial, with no sandbox product to safely execute code the agent wrote about itself.

09

Deployment

Single production environment; no staging tier planned pre-launch. Two independent auto-deploy paths from the same GitHub repo:

  • Agent runtime (Modal): every merge to main that touches agent/, sandbox_tests/, or governance/ triggers a Modal redeploy of the cron, webhook, and orchestrator.
  • Public site (Netlify): every push rebuilds and deploys ui/, independent of whether the agent runtime changed.

CI gate: .github/workflows/ runs the full sandbox_tests/ suite on every PR, autonomous or human-authored, before merge is possible — this is what makes a minor-change auto-merge safe to allow at all.

10

Rollout phases

Self-modification is the last capability turned on, not the first — it needs everything under it already proven.

Write the constitution

Before any code. A conversation, not a form — and it now has to carry the public-content boundaries that stand in for a per-post approval on Netlify.

Prove the loop, no self-editing

One agent, manually triggered, does a real task end to end on Modal + OpenRouter + GitHub, writes a log. No autonomy over its own code yet.

Add the triggers and Telegram

Hourly cron and message webhook go live on Modal with the run-lock in place. Telegram becomes the private approval channel; the Netlify public site goes live. Every code change still gets human PR review.

Turn on autonomous merges

Sandbox testing plus auto-merge for minor changes, with the constitutional lock enforced by branch protection from day one.

Let goals move

Sub-goals shift autonomously within the current mission. A top-level goal change is the first real test of the major-decision gate.

Widen the aperture

More subagents, more tool access, broader autonomy — earned by a clean run of prior phases, not scheduled.

Risks & open design questions

Points where this design made a default rather than a confirmed decision.

  • 1Constitution authorship process — drafted jointly or written solo for reaction? Affects Phase 0's shape before anything else can start.
  • 2Spend-cap response — daily OpenRouter ceiling amount, and whether hitting it also alerts same-day or only logs silently until the digest.
  • 3Constitution's scope — does it constrain every action, or only ones reaching the major-decision gate? Current default: every action.
  • 4Telegram allowlist value — the bot's single-user check has nothing to check against until Rinkesh's Telegram user ID is captured.
  • 5Operating hours — hourly tick around the clock, or bounded to hours Rinkesh is actually available to see a ping land.
  • 6Public content boundaries — resolved that Netlify publishing runs autonomously under the constitution rather than a per-post gate (§05), but the boundaries themselves aren't written yet: allowed topics, tone, hard lines on claims about real people, whether it can link out or only publish its own writing. This is now a hard dependency of Phase 0, not a nice-to-have.
