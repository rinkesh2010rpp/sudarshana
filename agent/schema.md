# Memory-compile schema — the compile spec (v2)

Single source of truth for the knowledge layer and the compile pass that
maintains it. The system prompt only says *when* to compile; every rule for
*how* lives here. Versioned in this repo, reviewed in the same PR as any code
that enforces it. This file governs the *derived* pages under
`/data/memory/knowledge/`; it does not live there (that is derived data and
would risk being clobbered).

v2 (2026-09-27) replaces v1: pages are single-claim nodes in a sparse link
graph, `index.md` and `lint.md` are generated by code, and each new fact gets
an explicit operation instead of being appended. Pattern after Karpathy's
LLM Wiki (raw sources → wiki → schema; ingest / query / lint).

## Purpose

Distill the accumulated logs into durable, interlinked, single-concept pages a
cold cycle can use without re-deriving knowledge from the logs each time. Pages
are a **cache of ground truth**, never a replacement for it. The canonical
`/data` files (logs, decisions.md, actions/, ROADMAP.md, INBOX.md, VISION.md)
always win on disagreement.

## Layers

- **Raw sources** — `/data/logs/*.md`, `decisions.md`, `actions/`. The compile
  reads them and never edits them for the wiki's sake.
- **The wiki** — the pages under `/data/memory/knowledge/<type>/`. Written by
  the compile.
- **This schema** — the rules.

## Layout

All under `/data/memory/knowledge/`:

- `concepts/<slug>.md` — durable patterns, failure modes, working rules.
- `system/<slug>.md` — how the runtime actually behaves (model timing, git
  auth, the conversation checkpointer). "How this environment works, so I
  don't re-learn it cold."
- `built/<slug>.md` — one entry per thing that exists: what it is, where it
  lives, current status. Not its history — history stays in `actions/` and
  the logs.
- `lessons/<slug>.md` — durable corrections from `Lessons:`-flagged log
  entries (see "Lessons" below).
- `index.md` — **generated by code, never edit.** One line per page: path —
  title. Injected into every model call.
- `lint.md` — **generated by code, never edit.** The current list of pages
  that break this schema. Rewritten, not appended.
- `log.md` — the wiki's own changelog, append-only, written by the compile
  (see "log.md").
- `.last-compiled` — one line, the newest **closed** log date compiled
  through (e.g. `2026-09-03`). Only closed logs dated after it are read.
  Absent = read all closed logs.

Code regenerates `index.md` and `lint.md` at the end of any turn in which a
page changed, so edits show up in the index from the next turn on.

## Page format

Every page is exactly this shape. Code parses it, so keep the line prefixes
exact.

```
# <The claim, as one sentence, ≤120 characters>

<Body: when it applies, how to check it, exceptions, what to do.
 Whole page ≤1 KB.>

Evidence: <canonical path>, <canonical path>
Related: <slug>, <slug>
Added: YYYY-MM-DD · Updated: YYYY-MM-DD
Superseded-by: <slug> (YYYY-MM-DD)
```

- **Title = the claim.** Write the statement itself ("Turns die at the 1500s
  Modal cap — write durably as you go"), not a topic name ("Timeout cap").
  The title is also the page's index line, so it must stand on its own.
- **Single-concept test:** if the page cannot be stated in one sentence, or
  would answer two unrelated questions, it is two pages.
- **Evidence** — required. Pointers to the canonical files the claim rests on
  (`logs/2026-09-13.md`, `decisions.md`, `agent/main.py`). Point, never
  retell: the incident story stays in the log.
- **Related** — optional, **at most 5**, most related first, **forward only**:
  list the pages this one leans on. Do not edit the other page to add a link
  back; code computes inbound links when it needs them. Slugs are unique
  across all four types, so a bare slug is enough.
- **Added / Updated** — required. `Added` never changes; `Updated` is the date
  of the last real change to the claim or body.
- **Superseded-by** — only when the claim is no longer true (see
  "Operations"). The page stays as history; code drops it from the main index
  and lists it under "superseded".

## Naming

- kebab-case slugs, semantic names, one concept per page.
- No dates in filenames (dates churn; the logs carry them).

## May not contain

- Claims without an Evidence pointer (dropped next compile).
- Retold log prose or incident narratives — link the log instead.
- Change history ("★ CORRECTED", "EXTENDED", "SUPERSEDED" notes) — use an
  operation (update / supersede) instead.
- Opinions about people; claims about anyone else.
- Anything already held elsewhere (state.md, decisions.md, actions/, ROADMAP).

## Coverage policy

Distill only what a cold cycle would otherwise re-derive; everything else stays
in the logs. Absence of a page is a designed answer (grep the logs), not a
failure.

- **SELECT** — test: "would this take >1 read to reconstruct from logs alone?"
  If no, grep handles it. Distill: runtime facts that don't change (system/),
  durable patterns and failure modes (concepts/), registry of what exists
  (built/).
- **AVOID** — anything the logs answer in one grep; anything state.md already
  holds; volatile status (PR state, today's task); opinions, speculation, bare
  claims; restated prose; anything decisions.md / actions / ROADMAP hold.
- **HEALTH** —
  1. Traceability: every page carries Evidence; bare claims are dropped.
  2. Regenerability: a page is short enough to rebuild from its Evidence in
     one pass; a page longer than its sources has drifted.
  3. Canonical wins: pages are derived, never authoritative.
  4. Conservatism: unsure = don't create; the log keeps it for a later pass.

## Operations

### Compile (ingest)

One bounded pass per cycle:

1. Read this file and follow it exactly; if missing, record that and stop —
   do not invent rules.
2. Read `lint.md`. Issues on pages you touch this pass get fixed as you go.
3. Read `.last-compiled`; read only **closed** logs dated after it — a log
   is closed once its date is before today (by the injected current time).
   Never compile today's log: it is still growing, and a marker set to today
   would skip every entry written after the pass. A few days at most per
   pass.
4. For each durable fact in those logs, find the page(s) it concerns (the
   index lists every page by path and claim) and choose exactly one
   operation:
   - **ADD** — a new concept: create a page in the format above.
   - **UPDATE** — the fact refines an existing page's claim or body (better
     detail, new Evidence, a new exception). Edit in place, bump `Updated`.
     If the page would outgrow 1 KB or stop passing the single-concept test,
     split it instead (ADD the new concept, trim the old page).
   - **SUPERSEDE** — the fact shows an existing claim is no longer true.
     ADD (or UPDATE) the page with the true claim, and add
     `Superseded-by: <that slug> (date)` to the old page. Do not rewrite the
     old page's history.
   - **NOOP** — already covered, or fails the coverage policy. Nothing to
     write.
   One log entry can touch several pages.
5. For each page you ADD or UPDATE, set `Related` to its most related pages
   (≤5, forward only).
6. Set `.last-compiled` to the newest log date compiled — always a closed
   day, never today.
7. Append one line to `log.md` (format below) and one line to today's
   `/data/logs/<date>.md` saying a compile pass ran.

The compile writes pages, `.last-compiled`, `log.md` and the daily log line
**only**. It never edits `index.md` or `lint.md` (code owns them) or
`state.md` (the cycle-end refresh owns it).

### Review (judgment lint)

Code catches format problems; only judgment catches meaning problems. When a
compile pass finishes with room to spare, review the pages it touched plus
their Related pages for:

- two pages whose claims contradict → SUPERSEDE the wrong one;
- a claim the logs have since overtaken → UPDATE or SUPERSEDE;
- a concept the logs keep mentioning that has no page → ADD.

Record any change as its own `log.md` line (`review`).

### Query → file back

When a turn produces a durable insight (not only a correction), it may be
filed as a page by the next compile: mark it in the day's log with a
`Lessons:` flag or a plain "durable:" note so the compile finds it.

## log.md

Append-only, one line per compile or review pass, newest last:

```
## [YYYY-MM-DD HH:MM] compile | logs 09-25..09-26 | +concurrent-turns ~timeout-cap ⤳old-slug =3
```

`+slug` ADD · `~slug` UPDATE · `⤳slug` SUPERSEDE (the superseded page) ·
`=N` NOOP count.

## Lessons

A log entry carrying a `Lessons:` flag (slug + what-was-wrong → the-correction)
becomes a `lessons/<slug>.md` page via the operations above, subject to the
future-need gate: store only if likely needed for a future case; a one-off
stays in the logs. A correction already generalized in concepts/ or system/
is not duplicated here.

## Cadence

- Self-task, like the daily blog: whenever a cycle has no higher-priority
  work (INBOX empty, no real step on the active initiative — being blocked on
  Rinkesh's approval is fine), check `.last-compiled`; if any closed log is dated
  after it, run one compile pass, then stop for that cycle.
- Incremental and bounded: only logs since the last compile; a backlog drains
  over quiet cycles rather than one marathon.
- Pre-approved and /data-internal: does not wait on Rinkesh.

## Retrieval

- `index.md` rides along on every model call (with state.md), so every
  page's claim is always visible. Open a page with `read_file` on the path its
  index line gives when you need the body or its Evidence.
- Superseded pages are listed separately at the bottom of the index; read
  them only for history.
- A topic with no page is an answer too: grep the logs.
